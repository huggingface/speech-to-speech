# Committed user-input observations

An internal WebSocket proxy can request a payload-free observation of accepted
input, including input that never produces a response. This is an optional
speech-to-speech extension, independent of terminal response latency.

Send this header when connecting to `/v1/realtime`:

```text
x-speech-to-speech-user-input-observation: 1
```

Only that exact version opts in. Existing WebSocket clients and WebRTC sessions
receive no new events. Client session settings and metadata cannot enable it.
A requested header is not evidence that a server supports the extension: wait
for `speech_to_speech.user_input.observation_started`, sent after
`session.created` on an opted-in connection.

```json
{
  "type": "speech_to_speech.user_input.observation_started",
  "version": 1,
  "event_id": "user_input_session_example_0",
  "session_id": "session_example",
  "timestamp_s": 1790000000.0,
  "dropped_events": 0,
  "sequence": 0
}
```

An accepted input produces:

```json
{
  "type": "speech_to_speech.user_input.accepted",
  "version": 1,
  "event_id": "user_input_session_example_1",
  "session_id": "session_example",
  "timestamp_s": 1790000001.25,
  "dropped_events": 0,
  "sequence": 1,
  "input_kind": "speech"
}
```

`session_id` is generated by the server for the actual engine connection. It is
not a client session setting or an allocation ID from an external load balancer.
`sequence` increases once per accepted item observed on that connection and
resets only for a newly registered connection with a new server session ID.
`event_id` is stable for that session/sequence. Receivers can deduplicate retries
with `(session_id, sequence)` and independently retain their own trusted external
session/source association. Sequence and drop counters saturate at `2**53 - 1`;
exhaustion drops observations instead of reusing an event identity.

`timestamp_s` is server UTC seconds when the service observes the accepted
commit. It is not audio time, client time, provider response time, or a receiver's
receipt timestamp. It uses the wall clock and can jump. Speech and normal direct
audio are observed when their existing held input terminal publishes. A
protocol-neutral direct-audio pipeline without a wire input lifecycle observes
its existing tracker commitment at a later event drain; that delay is not an
exact timestamp of the tracker's internal mutation. Observation never commits a
turn itself. Consumers needing receipt timing or clock-skew detection must record
their own receipt clock as a separate fact.

## What counts

An observation means meaningful input was accepted in the session's **default
conversation**, at its existing mutation or publication gate:

- A nonempty user-role text, image or audio item successfully added with
  `conversation.item.create`, including deferred items only when actually applied.
- Each successfully applied user item in an in-band `response.input` batch. The
  validation copy does not count; a later actual application failure does not
  erase a preceding successful application.
- A nonempty final speech transcription whose input terminal commits, whether or
  not automatic response generation is enabled.
- Nonempty finalized direct audio that is accepted into retained history or a
  generation request and reaches its corresponding existing commit gate.

`input_kind` is `text`, `image`, `audio`, `mixed` (one user item containing more
than one meaningful modality), or `speech` (recognized pipeline speech). One
inline request can therefore produce multiple input observations. A supplied
user-role history item counts too: this protocol does not infer human intent or
distinguish replayed history from new interactive text.

Partial transcriptions, speech onset, tentative pauses, superseded revisions,
empty/failed speech transcription, blank text, rejected input, assistant/system
items, tool calls/results, empty response requests and out-of-band private
response input do not count. Removing an already accepted text item later does
not retract the historical acceptance; deleting a provisional speech item before
its commit prevents that observation. Input acceptance does not imply successful
LLM generation, output delivery, a complete conversation, a person, or a DAU.

The extension does not retain or emit text, transcript, content hashes, audio,
images, client item IDs, tool payloads, arbitrary metadata, credentials or URLs.
The observation state contains only fixed technical fields and shares the actual
connection's lifetime. Existing terminal-input state carries its fixed kind;
protocol-neutral direct audio uses a revision marker on existing turn accounting.
Neither introduces an independent registry of input items.

## Delivery and coverage

This is a bounded, best-effort observation stream, not a durable event log or an
acknowledged delivery protocol. The queue holds at most 64 observations per
connection, including its capability event, and rejects new observations when
full. Ordinary accepted input is never rolled back by observation failure. The
existing client dispatch and pipeline send loop drain bounded batches through
the existing transport send lock. No extra provider call, inference, task owner,
thread, global history or periodic network probe is introduced.

`dropped_events` reports cumulative **locally known** observation losses: queue
capacity, invalid observation clocks/construction, and send exceptions or
cancellation visible to the observation sender. Every retained event gets the
latest count when drained. Later sequence gaps can reveal missing accepted
observations. A transport may itself suppress an error, a receiver may disconnect,
and process/session shutdown can lose queued or in-flight observations. Those
losses are not necessarily reflected in the last received drop count. The
existing transport can wait on its lock or I/O; this extension promises no hard
send deadline. A failed send has no replay/acknowledgement buffer here.

Capability receipt proves support on that connection, not full fleet coverage or
that zero observed events means no user supplied input. Consumers should expose
missing capability, sequence gaps, drops and process/delivery gaps. Historical
servers or unnegotiated connections are unavailable instrumentation, not known
zero. A downstream metric should count distinct trusted allocated session IDs
with received accepted-input events in its explicitly stated event window; it
must not sum minute distinct counts, infer inputs from terminal responses, or
present the result as unique humans. Archive durability, cross-process replay,
external callback authentication and dashboard coverage belong to that downstream
consumer and are not implemented by this upstream extension.
